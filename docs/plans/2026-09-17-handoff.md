## 1. Projeto e regras que continuam valendo

O gasclaw é um framework agêntico que roda **100% no Google Apps Script**. Cada agente é uma pasta do Google Drive
com markdown; o PC somente compila TypeScript, testa e publica com `clasp`.

Regras não negociáveis de `CLAUDE.md`:

- zero servidor externo;
- agente = pasta do Drive, sem executar código vindo dela;
- `minimal-code` ativo;
- toda melhoria relacionada a limites do GAS exige POC medida em `poc/` e decisão registrada em ADR;
- operação depois do setup passa por `./gasclaw`;
- não declarar algo resolvido, publicado ou medido sem evidência fresca do teste real correspondente;
- conteúdo e documentação do projeto em pt-BR; identificadores de código em inglês.

O projeto usa devmode + Conductor. O track atual é
`conductor/tracks/p2-chat-assincrono/`. Os critérios desse track continuam abertos até a POC real passar.

O usuário enviou duas vezes no Google Chat:

```text
o que eu tenho na agenda do gabriel.br@gmail.com? tem duas agendas lá, me traga tudo que temos para essa semana
```

```text

```

As tentativas se repetiam aproximadamente a cada 39 segundos. A causa foi comprovada: mensagens normais ainda
entravam no `handleChat` síncrono; somente `/poc p2` usava o caminho novo. Repetir a pergunta apenas gerava outro
timeout.

Correção publicada na v77: mensagens `MESSAGE` normais agora validam acesso, criam um `DurableRun`, persistem o
destino da entrega e devolvem `pensando...` sem chamar o LLM dentro da janela do evento. O LLM e as tools rodam no
worker de um minuto.

Isso ainda precisa ser verificado ao vivo depois das autorizações. Os testes locais não substituem esse teste.

## 4. O que foi implementado nesta janela

### Entrada assíncrona normal

`src/chatAsync.ts` implementa a aceitação rápida:

- valida kill switch, agente, chave, texto e acesso;
- usa o nome autenticado da mensagem como `runId` estável;
- trata retry do mesmo evento sem substituir a `requestId` existente;
- persiste o run antes de responder;
- guarda espaço e thread originais;
- retorna `pensando...` com `MARKUP_SYNTAX_MARKDOWN`.

`src/main.ts::onMessage` usa esse caminho para mensagens normais. `/poc p2` continua restrito ao dono e ao build
dev. Cliques de card continuam no caminho específico de aprovação.

### Entrega durável pelo Chat API

`src/chatDelivery.ts` adiciona ao `DurableRun`:

- `space`, `thread`, `requestId`, `notBefore`, `status`, `messageName` e `sentAt`;
- entrega somente para runs `done` ou `failed`;
- texto final sanitizado por `safeChatMarkdown`;
- `markupSyntax: MARKUP_SYNTAX_MARKDOWN` para o Google Chat renderizar `**negrito**` em vez de exibir os asteriscos;
- menções ativas como `<users/all>` neutralizadas antes do envio;
- checkpoint `sent` somente depois de resposta 2xx.

`src/runner.ts` foi corrigido para manter um run terminal na fila enquanto a entrega ainda estiver `pending`.
Antes dessa correção, uma morte do GAS entre finalizar o run e enviar ao Chat removia o ponteiro e perdia a
resposta definitivamente. Agora a fila só é removida depois do recibo `sent`; retry reutiliza a mesma `requestId`.

### Cliente IAM/Chat sem chave privada

`src/chatApi.ts` é o núcleo HTTP injetável; `src/chatApiGas.ts` é a borda `UrlFetchApp`:

- usa `ScriptApp.getOAuthToken()` para chamar IAM Credentials;
- emite token efêmero com escopo `chat.bot` para a service account dedicada;
- cria e lê mensagens reais pelo Chat API;
- não persiste access token nem chave privada;
- erros não ecoam corpo potencialmente sensível.

Foi feita uma prova preliminar real, fora da POC final: IAM emitiu token `chat.bot`, o app encontrou a DM e publicou
um card real como app. A mensagem criada foi
`spaces/SPACE_ID_REDACTED/messages/aMC6ZjyT9Vs.aMC6ZjyT9Vs`. Isso provou o mecanismo básico, mas não fecha os critérios
temporais/idempotentes da P2.

### Provisionamento mínimo

`gasclaw::ensure_chat_identity` no dev:

- habilita `iamcredentials.googleapis.com`;
- cria/reusa `gasclaw-chat@gasclaw-dev-example.iam.gserviceaccount.com`;
- cria ou atualiza o papel customizado `gasclawChatTokenMinter` com somente
  `iam.serviceAccounts.getAccessToken`;
- substitui a policy da service account por exatamente um binding para `user:owner@example.com` nesse papel;
- não cria arquivo de chave;
- embute somente o e-mail público da service account no bundle dev.

O escopo IAM é adicionado pelo `build.mjs` apenas quando `GASCLAW_DEV=1`; prod continua sem ele.

### POC P2

`./gasclaw poc p2`:

1. reconcilia a identidade e publica dev;
2. espera o protocolo correto;
3. confirma token do app, DM e trigger `drainRuns` ativo;
4. pede o envio exato de `/poc p2` na DM;
5. cria `pensando...` e um run terminal com entrega após pelo menos 120 s;
6. simula morte depois do POST e antes do checkpoint sem depender de código de recuperação da execução morta;
7. repete a mesma `requestId` e exige o mesmo `message.name`;
8. lê as mensagens reais com `messages.get`;
9. valida estruturalmente o card, Markdown, neutralização de menção, zero chave `USER_MANAGED`, policy exata e zero
   material secreto no repositório/bundle.

Importante: `messages.list` foi removido porque app auth com `chat.bot` não o suporta. A POC guarda o
`message.name` retornado por `create` e o confirma com `messages.get`, que suporta `chat.bot`.

### Formatação e link do Apps Script

- Respostas do Chat usam o subconjunto Markdown documentado pelo Google Chat e o campo `markupSyntax`; isso é a
  correção para os `**` literais.
- O painel já mostra o link **Apps Script** ao lado do link da pasta do Drive de cada agente. Isso está em
  `settingsState().scriptUrl`, `src/settings.html` e `test/main-links.test.ts`, e está incluído na v77.

Três revisores independentes analisaram segurança, testes e complexidade. Achados corrigidos:

- uso incompatível de `messages.list` com `chat.bot`;
- mensagem normal ainda síncrona;
- perda da fila entre término do run e envio;
- `waiting`/`paused` considerados falsamente terminais;
- policy IAM e papel customizado não reconciliados de forma exata;
- preflight sem verificar trigger;
- busca textual frouxa pelo card em vez de validação estrutural;
- POC que reenfileirava manualmente depois da “morte”, mascarando a janela real.

Risco ainda aberto, não esconder: o estado do run e seu destino ficam na pasta do agente, que pode ser compartilhada.
Um editor dessa pasta já pode alterar prompt/configuração e também poderia alterar um JSON de run pendente. A
revisão sugeriu pasta owner-only ou MAC para o envelope privilegiado. Isso não foi resolvido nesta janela; precisa
de decisão de trust boundary antes de virar mudança de arquitetura.

Limitação funcional ainda aberta: `waiting` e `paused` não são entregues como resposta final. Logo, um run do Chat
que peça aprovação, faça `ask` ou pause por orçamento pode ficar apenas em `pensando...`. `ask` já estava fora do
escopo da P2; aprovação assíncrona precisa ser tratada antes de chamar todo o Chat assíncrono de completo.
